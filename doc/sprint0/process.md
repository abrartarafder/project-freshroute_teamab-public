## How did you organize the team? Which tools did you use, if any? 

We first organized the team by collectively identifying the main goal of the project and agreeing on the overall idea we wanted to build. Once we aligned on the objective, we discussed the core features and target users to ensure everyone had a clear understanding of the system’s direction.

After defining the scope, we divided responsibilities based on individual strengths and skill sets. For example, members who were more comfortable with frontend development focused on UI components, while others with backend or logic experience handled data models, routing, and state management. Each user story had one primary developer responsible for implementation, while other team members reviewed pull requests before merging. Documentation and backlog refinement were handled collaboratively.

### Tools Used

- **GitHub** – Version control, feature branches, pull requests, and code reviews.
- **Trello** – Sprint planning, backlog tracking, and task assignment.
- **Discord** – Hosting team meetings and live discussions.
- **WhatsApp** – Ongoing communication and coordination.
- **Markdown files / Google Docs** – Shared documentation (summary.md, done.md, process.md).

This structure allowed us to balance workload effectively while maintaining clear communication and accountability.

## How did you make decisions? 

We aimed for consensus-based decision making.

- Technical decisions were discussed briefly during meetings.
- If disagreement occurred, we compared the pros and cons for the options. 
- When necessary, we voted informally.
- For small implementation details, the assigned developer made the final call.

We prioritized clarity, feasibility within Sprint 0, and alignment with the project scope.

## How did you define priority and/or points of user stories? How many rounds of voting (on average) did you need to come to a consensus for the point estimate? 

We prioritized user stories based on:

1. Core system flow (browse → cart → checkout → order)
2. Dependencies between features
3. User value
4. Implementation complexity

Foundational features (product listing, cart, checkout) were completed before enhancements.

### Story Point Estimation

- We used relative estimation (simple comparison between stories).
- We assigned higher points to stories with:
  - Backend + frontend integration
  - Complex state handling
  - Validation logic
- Smaller UI-only tasks received lower points.

On average, it took **1–2 rounds of discussion** to reach consensus on a story’s point estimate. If there was disagreement, we briefly explained reasoning and adjusted accordingly.

## How frequently did you meet? 

- We met **once per week formally** for sprint planning and progress review.
- Additional short check-ins occurred as needed.
- Communication remained active throughout the week via private messaging and discord chats with one another.
- The formal meeting on discord was to ensure that everyone was completing their tasks on time and those who needed extra help were recieving it as needed from those who had free time to allocate. 

## What lessons should you take forward to the next phase? 

The main lessons that we should take forward going into the next phase is that sometimes it becomes harder to gauge the amount of time that a task will take or how many people a task will require in order to be completed thoughtfully. This makes reallocation a lot more difficult and requires reallocation to be done closer to the due date. Ideally, a brief overview of the task and reallocating as needed would be a smarter approach. 

Another lesson that we would take going forward is to discuss the changes thoroughly with another and making sure to always pull each other's changes on Github as there can always be merge conflicts and issues when changes are not pulled and implemented correctly.
